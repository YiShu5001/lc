# 项目整体实现计划

本文件用于规划 `lc` 仓库从“论文主链路已初步建立”推进到“可持续开发、可运行、可验证、代码与论文一致”的完整实现过程。

目标不是一次性大改，而是按主线逐步收敛，使第三章、第四章、系统桥接、实验入口、测试体系和论文表述共同稳定下来。

## 1. 总目标

项目的最终目标是实现以下状态：

- 所有论文主链路执行代码统一收敛到 `src/lc/`
- 第三章控制层、第四章规划层、系统桥接层都有明确且可运行的主实现
- `experiments/` 作为论文实验入口，`tests/` 作为接口与回归验证入口
- `main.py` 与 `examples/` 不再依赖旧目录，或明确归档为 `legacy`
- 论文中的第三章、第四章方法描述与实际代码结构严格对齐
- 仓库 README、章节说明文档、实验脚本、测试与源码形成闭环

## 2. 当前状态判断

### 已完成基础

- `src/lc/control`、`src/lc/planning`、`src/lc/system` 已建立章节接口
- 第四章模型主口径已对齐到 `MultiUAVModel`
- `experiments/control`、`experiments/planning`、`experiments/integrated` 已可调用 `src` 主链路
- `tests/smoke/test_chapter34_interfaces.py` 已覆盖基础接口验证
- 第四章论文网络描述已与当前双阶段结构完成一轮对齐
- README 与章节总纲文档已建立

### 未完成问题

- `main.py` 仍依赖 `Gym_env`、`NN`、`Reinforce_learning`、`Trainer`
- `examples/` 仍大量走旧链路
- `src/lc` 仍有占位目录、重复抽象和待迁移骨架
- 第三章控制层接口仍偏演示化，尚未形成完整训练/实验闭环
- 第四章课程学习、奖励设计、Critic、训练编排在 `src` 主链路中还不完整
- 论文与代码虽然已有映射，但还没有完成“每章对应完整实现”的最终收束

## 3. 实施原则

- 以 `src/lc/` 为唯一目标主链路，不再新增新的旧式目录实现
- 所有重要代码变更都必须同时检查第三章/第四章论文表述
- 优先保证主链路可运行，再处理历史目录清理
- 优先保留论文所需的明确结构，不做无关的大而全框架扩张
- 每个阶段都应形成“代码 + 实验 + 测试 + 文档”的闭环

## 4. 分阶段实施

### 阶段 A：主链路梳理与迁移基线建立

目标：

- 明确 `src/lc` 中哪些模块是保留项，哪些是占位项，哪些是旧目录替代项
- 建立统一的迁移边界，避免后续继续在旧目录上叠加实现

要做的事：

- 清理 `src/lc/**/__pycache__` 与 `.pyc`
- 标记并处理 `src/lc` 中无实现的占位目录
- 形成旧目录到 `src/lc` 的迁移映射表
- 为 `Gym_env/`、`NN/`、`Reinforce_learning/`、`Trainer/` 明确后续命运：
  - 迁移
  - 保留为 legacy
  - 删除

验收标准：

- `src/lc` 目录职责清晰
- 不再存在明显误导性的空壳主链路目录
- 迁移路线被文档化

### 阶段 B：第三章控制层完整实现

目标：

- 将第三章从“接口演示”推进为“完整控制层主链路”

要做的事：

- 在 `src/lc/control` 下补齐控制层配置、控制器适配、训练接口与实验入口
- 明确 RL-LADRC 的状态、动作、奖励、安全裁剪和回退机制
- 将跨时间样本增强机制收敛到 `src` 主链路实现
- 为第三章建立独立可运行的实验脚本和 smoke/regression tests
- 将第三章论文文字与代码对象逐项对齐

验收标准：

- 第三章主方法能通过 `src` 主链路独立运行
- 控制层至少具备一个完整实验闭环
- 第三章关键名词、模块和论文描述与代码一致

### 阶段 C：第四章规划层完整实现

目标：

- 将第四章从“主模型已对齐”推进为“规划层完整训练与实验主链路”

要做的事：

- 固化 `MultiUAVModel` 为论文图主实现
- 补齐第四章所需的 Critic、课程学习、奖励设计和训练编排模块
- 明确 `TaskDecomposedActor` 为轻量化实验接口，不再承担主实现职责
- 补充规划层的训练入口、评估入口与可视化接口
- 为字典输入、扁平输入、课程切换、记忆采样等建立更完整测试
- 将第四章论文结构、代码结构与实验脚本完全对齐

验收标准：

- 第四章训练/实验可通过 `src` 主链路独立运行
- 课程学习与金字塔经验池不只是接口存在，而是进入训练闭环
- 第四章论文中的主方法均能在代码中找到明确对应对象

### 阶段 D：章节桥接与系统集成

目标：

- 将第三章和第四章从“并列存在”推进为“系统闭环协作”

要做的事：

- 规范规划层到控制层的动作接口映射
- 统一章节桥接配置、桥接实验入口与桥接测试
- 明确桥接层输入输出、阶段频率和中间表示
- 将系统级实验与论文章节总结保持一致

验收标准：

- `chapter34` 桥接可以稳定运行
- 规划层输出与控制层输入不存在命名或维度歧义
- 论文可以用单一系统图解释整篇主方法

### 阶段 E：主入口迁移与旧目录退场

目标：

- 让仓库真正从旧目录迁移到 `src` 主链路

要做的事：

- 将 `main.py` 依赖逐步替换到 `src/lc`
- 将 `examples/` 迁移为调用 `src` 的实验/示例入口
- 给旧目录增加 `legacy` 标识，必要时移动到归档区域
- 删除不再需要的重复实现

验收标准：

- 至少一个统一训练入口完全基于 `src`
- `examples/` 不再依赖旧目录主实现
- 旧目录不再被误认为主链路

### 阶段 F：文档、论文与发布级整理

目标：

- 让仓库进入“别人看得懂、你自己以后也维护得动”的状态

要做的事：

- 维护 README、章节总纲、迁移说明、实验说明
- 检查第三章和第四章 `.tex` 与最终代码命名一致
- 为主要实验结果、图表、脚本和测试建立索引
- 统一仓库中的术语口径

验收标准：

- README 能独立解释项目定位、目录职责、运行方式和迁移状态
- 第三章、第四章文字与代码不再互相打架
- 新协作者能根据文档快速定位主链路

## 5. 关键交付物

项目实施完成后，至少应交付以下结果：

- `src/lc/` 下完整的控制层、规划层、桥接层主链路实现
- 统一的训练/实验入口
- 稳定可跑的 `experiments/`
- 分层清晰的 `tests/`
- 与代码一致的第三章、第四章论文正文
- 完整 README、章节总纲和迁移说明文档

## 6. 风险与注意事项

### 代码风险

- 新旧目录并行时间过长，容易造成双维护与表述冲突
- 如果先删旧目录再迁移，会导致大量入口失效
- 如果只做接口不做训练闭环，会形成“看起来完整、实际不可用”的假实现

### 论文风险

- 如果代码名改了但论文没改，容易造成盲审和答辩阶段不一致
- 如果论文写得过强，但代码还只是接口或 demo，会形成过度宣称

### 迁移风险

- `main.py`、`examples/`、旧训练器之间耦合较深，迁移需要分步而非一次性替换

## 7. 建议执行顺序

推荐按照以下顺序真正开始实施：

1. 阶段 A：主链路梳理与迁移基线建立
2. 阶段 B：第三章控制层完整实现
3. 阶段 C：第四章规划层完整实现
4. 阶段 D：章节桥接与系统集成
5. 阶段 E：主入口迁移与旧目录退场
6. 阶段 F：文档、论文与发布级整理

## 8. 计划文件的用途

这个文件是“整个项目实现”的总计划，不是某一轮单点任务清单。

你后续可以用它做三件事：

- 作为总体路线图，决定先做哪一阶段
- 作为代码和论文同步时的检查表
- 作为后续拆分子任务时的母计划文档

## 9. 当前建议

如果要开始真正推进实现，最合理的第一步不是立刻重写所有代码，而是：

- 先做阶段 A，把 `src` 主链路边界和旧目录迁移策略彻底钉住
- 然后先完整做第三章，再完整做第四章

原因是：

- 第三章与第四章已经是你论文的稳定主线
- 这两章决定了 `src/lc` 最终该长成什么样
- 如果不先明确章节主链路，后续迁移很容易又回到旧框架思维里
